## 1.0在岗的2个bot详细说明

### bot-01 哨兵（健康巡检）
**职责边界**：只负责"发现故障"，不负责修。
```
每30秒（可配）：ping所有渠道
  ├─ 哪个渠道通了 → 标🟢
  ├─ 哪个渠道超时/报错 → 标🔴
  └─ 结果写入共享状态（给调度用）
```
**为什么1.0必须有它**：我们要"填一个渠道验证一个"，哨兵就是验证工具。填了DeepSeek → 哨兵去ping → 通了标绿。**这是接下来"建表填渠道"时干活的bot。**

**不做什么**：不比价、不切换、不采购。只盯健康。

### bot-02 接入（渠道采购+配置生成）
**职责边界**：负责"把新渠道接入进来"+"生成配置指南"。
```
职责1·渠道接入：
  读取上游渠道表 → 配置到New-API → 跑通测试 → 标记可用
  
职责2·配置生成：
  参考 apiyi/V-API 的配置指南结构
  → 用AIXX自己的base_url重写
  → 生成给用户agent用的配置文档
```
**为什么1.0必须有它**：我们"一个个往里填"渠道时，接入bot负责把表里的东西真正配进系统。**填表=接入bot干活。**

**不做什么**：不做健康巡检（那是哨兵）、不做比价（那是比价bot）。

## bot协作机制（2.0+设计，1.0暂不实现）

```
请求进来
   ↓
调度bot问：哨兵，谁健康？比价，谁便宜？
   ├─ 哨兵返回：渠道A🔴故障，渠道B🟢健康
   ├─ 比价返回：渠道B最便宜
   └─ 调度决策：走渠道B
   ↓
执行调用 → 记账bot扣费
```

**关键设计**：bot之间通过"共享状态"通信（不是直接调用），任何一个bot挂了，其他bot用缓存数据继续跑。

## 添加/修改/删除bot的原则

1. **加bot**：新岗位出现需求 → 在表里加一行 → 实现独立部署（Docker容器或独立服务）
2. **改bot**：职责边界要清晰，一个bot只干一类事。职责蔓延了=该拆成两个bot
3. **删bot**：功能废弃 → 标"已退役"不删记录（留历史）
